# 4. Windows app

Python 3.13, packaged with PyInstaller (`--onedir --windowed`) and an Inno Setup installer. Source in `windows/`. Overview of processes and threads: [02-architecture.md](02-architecture.md).

## Entry point (`windows/vox_app.py`)

| Command | Result |
|---|---|
| `Vox.exe` / `python windows\vox_app.py` | Starts the engine. If mutex `Local\VoxEngine` is already held, only opens the window (`engine.open_window`). Logs to `vox.log`. |
| `Vox.exe --window` | Opens the main window. If mutex `Local\VoxWindow` is held, focuses the existing window instead. Logs to `window.log`. |
| `Vox.exe --relay [relay options]` | Runs the relay server (`relay/relay.py`, `main(argv)` with the rest of the command line: `--data-dir`, `--port`, ...) and nothing else: handled first thing in `main`, before any GUI, audio or keyboard module is imported, so it needs no display. No mutex. Logs to `relay.log`. Started by the engine (see "Relay on this PC" below); you can also run it by hand. In the frozen exe the relay is bundled (`--paths ..\relay --hidden-import relay` in `build_app.bat` and the workflow); from source `vox_app.py` adds `..\relay` to the import path. |

The engine and window modes set DPI awareness, install `sys.excepthook` / `threading.excepthook` that log uncaught errors, and use a `RotatingFileHandler` (1 MB, 2 backups). See [11-logs-and-diagnostics.md](11-logs-and-diagnostics.md).

## Engine (`windows/engine.py`, class `Engine`)

### Hotkey behaviour

- Shortcuts (`ui_app.HOTKEYS`): Ctrl+Win (default, keys `ctrl_l` + `cmd`), Right Ctrl, Right Alt, Ctrl+Alt, Ctrl+Shift. Stored in `config.json` as a list of key names; `engine.KEY_ALIASES` maps names to pynput keys.
- **Keys that are not the user's shortcut:** keys a program sent (pynput's `injected` flag: Vox's own paste keys and Start-menu tap, but also AutoHotkey remaps and the on-screen keyboard) are ignored by `on_press`/`on_release` (ENG-5: with the Ctrl+Shift preset Vox's own Ctrl+Shift+V into a terminal started a recording). A short press of the dictation keys during which another key went down (`combo_other_key`: Ctrl+Win+Left, Ctrl+Shift+T) is another shortcut: on release it is cancelled, never latched, and does not count as the first tap of a double press; a hold of 0.3 s or more is still sent. AltGr is never Ctrl+Alt (ENG-6, issue 63): Windows reports it as a made-up Left Ctrl (scan code 0x21D) plus Right Alt, and the hook filter (`Engine._hook_filter`, pynput's `win32_event_filter`) drops that Ctrl; a Left Ctrl followed within 20 ms (`ALTGR_GAP`) by a Right Alt is dropped from `pressed` as well. So typing ł, ń, @ or { on a Polish, German or French layout neither starts the Ctrl+Alt preset nor the Ctrl+Alt+N note shortcut. Not run on a real AltGr layout.
- **The hotkey thread (R2-M1):** pynput calls `on_press`/`on_release` inside Windows' low-level keyboard hook, which must answer quickly. Once `Engine.run` started, they only put `(down, key, time)` on `_hotkey_q`; the `vox-hotkey` thread (`_hotkey_loop`) runs `_on_press`/`_on_release` in order, with the time of the event (`event_t`, so a slow microphone start does not turn a tap into a hold). A handler that raises is logged ("hotkey handler failed") and the thread goes on. Without the queue (tests) the handlers run at once.
- **Stale keys (R2-M2):** a key-up can be lost (Win+L locks the PC first, a secure desktop, sleep). When more than 2 s (`STALE_GAP`) passed since the last key event, `_check_gap` drops from `pressed` every key that `GetAsyncKeyState` says is up (`key_is_down`; a key that cannot be checked is kept), resets the main-key flags and ends a hold whose keys are gone. A held key repeats, so a real hold is never dropped. Not checked on a real desktop.
- **Hold to talk:** press starts recording (`start`), release stops (`stop`). A press shorter than 0.3 s (`TAP_SECONDS` = `hotkeys.HOLD_SECONDS`) is a tap; what it does is `hotkeys.tap_action`: with `hotkey_style` `classic` (default) the recording is cancelled and the tap time remembered; with `hold_or_tap` it keeps recording hands-free (`hands_free`, the pill shows the stop square, 18 minutes at most) until the next press sends it. An edit-by-voice instruction is never latched.
- **Keep listening:** a second tap within 0.5 s (`DOUBLE_TAP_GAP`) starts a keep-listening session (target Note or Type, setting `listen_target`, default Note), not a hands-free dictation; in `hold_or_tap` the latched recording of the first tap is cancelled first. A single press while it runs is ignored; a double press or the stop phrase ends it and saves what was said. Type can only be started with the double press, because it needs the app you are in (from the tray it is refused). Dictation limit is `MAX_SECONDS` (360 s).
- **Esc** cancels the recording in progress (hold, hands-free, voice note or instruction) or the keep-listening session (`Listening.cancel`: nothing more is sent, no note is saved, pieces already typed stay; a session of 30 s or more keeps its audio file for Recover). No flash: the pill just goes away. A session that is already saving is left alone. Esc still reaches the app in front.
- **Hands-free shortcut:** `hands_free_hotkey` (off by default, empty = off; for example `ctrl+cmd+h`. It used to default to Ctrl+Win+Space, which is also Windows' own "switch to the previous keyboard language" and is not blocked, so every start and end switched the layout for people with two keyboard languages). Pressed while the dictation shortcut has just started a recording, it latches it (`hands_free`); from idle it starts a hands-free recording; during one it stops and sends. When the held Ctrl+Win already ended the hands-free recording, the main key that follows does nothing.
- **Paste and copy last:** `paste_last_hotkey` (default Shift+Alt+Z) pastes the last dictation into whatever window is in front (`paste_text` with no target, so no window check); `copy_last_hotkey` (default off) puts it on the clipboard with the cloud-clipboard marker always, and out of Win+V history only when `clipboard_history` is off. The text is `Engine.last_text` (memory, set by every pasted dictation, not by notes, keep listening or edits) or the newest history entry with a text (only when `keep_history` is on). Runs on its own thread (`insert_last`), so the paste can wait for Shift+Alt to come up.
- **Edit by voice (experimental):** `command_hotkey` (default off), modifier keys only, for example Ctrl+Win+Alt. All of them down starts a recording marked `command_mode`; when they contain the dictation shortcut, adding the extra key within 1 s (`COMMAND_JOIN_SECONDS`) of the dictation starting turns that recording into an instruction. Letting go (`on_command_up`, or the dictation keys) calls `stop`, which hands the audio to `_process_command` instead of `_process`; see "Edit by voice" below.
- The extra shortcuts are parsed and checked together by `hotkeys.check(cfg)` (`Engine._chords`, re-read with the settings): a usable keyed shortcut is matched like the note shortcut (virtual-key code, never stored in `pressed`, `chord_keys_down` stops key repeat); a refused one is off and logged.
- **Note shortcut:** `note_hotkey` (default Ctrl+Alt+N, empty = off) toggles a keep-listening session with the target Note: one press starts, the next stops and saves, whatever `listen_target` says; a press while a session is saving does nothing. `session.note_hotkey(cfg)` parses it (a modifier of Ctrl, Alt or Win, Shift optional, plus one letter, digit or F1-F12) and refuses a combination that contains the dictation shortcut. The main key is matched by its virtual-key code (`engine.key_vk`) and never stored in `pressed`; `note_key_down` stops key repeat. The keys still reach the app in front. The engine re-reads the shortcut when the settings change. Details: [specs/p9e-keep-listening.md](specs/p9e-keep-listening.md).
- When the Windows key is part of the shortcut (or of a modifiers-only edit-by-voice shortcut), the engine taps virtual key `0xE8` so releasing Win does not open the Start menu. The tap is sent inside the keyboard hook (`_hook_tap`, which keeps its own small set of held keys), at the key-down that completes the shortcut and before that key is queued, so it always comes while Win is still down; on the hotkey thread it could come after Win was already released when that thread was busy opening or closing the microphone.
- `on_combo_down` ignores presses while `busy` (a dictation is being sent) and says so in a balloon, "Vox is still sending the last recording. Press again when the pill is gone." (at most every 5 s, `BUSY_TOLD_GAP`; ENG-3). `busy` ends as soon as the paste keys are sent: the old clipboard comes back afterwards on a thread (see Processing and paste).

### Recording (`Engine.start`, `_audio`, `stop`)

1. `start` refuses (with a tray notification, a red ! on the pill and by opening the window) if `core.endpoint_error(cfg)` reports a bad server address or `core.key_missing(cfg)` is true.
2. It remembers the foreground app's exe name (`foreground_app`, via psutil; the window title is never read); `paste` later checks the focused window against it.
3. It opens a `sounddevice.InputStream` (16 kHz, mono, int16) on the device chosen in Settings (`audio_devices.input_index(cfg["input_device"])`; empty means the Windows default). A chosen device that is missing, or fails to open, makes `_refresh_audio` restart PortAudio's device list (a microphone plugged in later), at most once every 30 s (`AUDIO_REFRESH_SECONDS`) and never while a stream is open or the warm microphone is being opened (`WarmMic.busy`, ENG-13); otherwise the Windows default is used. A stream that fails to start is closed at once (ENG-12). The "not connected" notice comes once until the device is back (issue 49, Windows 3). Since R2-M1 this runs on the hotkey thread, never in the keyboard hook.
4. `_audio` appends chunks and computes the level for the overlay.
5. `stop` calls `_end_recording` (atomic under `_rec_lock`, because the audio callback and the hotkey thread can both stop), joins the chunks, then:
   - shorter than 0.4 s (`MIN_SECONDS`): back to idle;
   - `core.is_silent(pcm)` (peak below 655 of 32768): notification "Vox did not hear anything (loudest sound N of 32768)…" and a red ! on the pill, back to idle;
   - an empty result after the speech and cleanup steps (a lone "Thank you.", "Bye." or "You" is filtered as a silence hallucination, or the server returned no words): notification "Vox heard no usable words in that recording…" and a red ! on the pill; no history entry and no paste (before 2026-10-05 this case was silent);
   - otherwise `busy`, and `_process` runs on a new thread.

### Processing and paste (`_process`, `paste`)

- Calls `core.process_detailed(cfg, pcm, exe, exe)` (see [06-pipeline.md](06-pipeline.md)). The app label given to the model is the exe name. The exe also decides code mode (`codemode.is_code_app`: an editor or terminal from `code_apps`, or the per-app style `code`; [15-code-mode.md](15-code-mode.md)); after the cleanup come the snippets (`snippets.py`) and, outside code mode, lists and pause paragraphs (`structure.py`).
- If cleanup was wanted but failed, a notification says the words were pasted as spoken. An answer that lost the spoken words (a summary or rewrite, `looks_valid` / `fidelity_ok` in `process_text`) counts as failed too: the words as spoken are used (spoken commands and dictionary replacements applied) and the notice ends with "the cleanup answer looked wrong". For that rejection (not for a failed call) the words as spoken also get a capital letter at the start and after each sentence end or line break (`fallback_text`), `Result.fidelity_fallback` is true, `_process` logs a `fidelity guard` warning and the history entry gets `"fidelity_fallback": true`. The strength is the Settings row "Cleanup strength" (`cleanup_strength`, Light unless set to `standard`; read through `clean_strength`; see [specs/p9a-cleanup-keeps-my-words.md](specs/p9a-cleanup-keeps-my-words.md)).
- `paste` calls `paste.paste_text(text, target, keep_clipboard, clipboard_history=..., background=True)` (`windows/paste.py`; every dictation goes through it: hold-to-talk, the keep-listening Type target and a recovered session; `target` is the exe name remembered when recording started):
  1. waits (up to 2 s, `MODIFIER_WAIT`, the pure `wait_released`; a timeout is logged) until Shift, Ctrl, Alt and Win are all up, so the paste is not combined with Win;
  2. compares the focused window's exe name (`GetForegroundWindow` and `QueryFullProcessImageNameW`, never the title) with `target`, ignoring case. If it differs, the text is left on the clipboard, **no paste keys are sent**, and the engine shows "Copied; the window changed". If the target was never captured, the window cannot be named, or the lookup fails (logged as a warning), the paste goes ahead rather than losing the text;
  3. when the focused window's program runs as administrator and Vox does not (`SystemDeps.foreground_elevated`/`self_elevated`, the token's `TokenElevation`), Windows would drop the keys (UIPI), so the text is only copied and `paste_text` returns `BLOCKED`; the engine explains once ("runs as administrator ... press Ctrl+V") and says a short line after that (R2-M6). When it cannot be told, the paste goes ahead. Not checked on a real elevated window;
  4. otherwise, only when `keep_clipboard` is off, reads the old text and takes a snapshot of the clipboard (every format that is plain memory: text, rich text, copied cells, images as DIB, file lists; `SystemDeps.clip_snapshot`; one format over 16 MB, `CLIP_FORMAT_LIMIT`, is left out and logged with its number and size; with `keep_clipboard` on nothing is read, because reading makes the copying program render every delayed format: issue 49, Windows 5), into a terminal (`TERMINALS`, below) makes the text one line first (`terminal_text`: line breaks and tabs become spaces, other control characters and ESC are dropped, so the paste never runs a command; SEC-1), copies the text with `SystemDeps.clip_set` (own Win32 calls, not pyperclip; it always sets the format `CanUploadToCloudClipboard` = 0, so the cloud clipboard never gets the dictation, and, only when `clipboard_history` is false, also `ExcludeClipboardContentFromMonitorProcessing` and `CanIncludeInClipboardHistory` = 0, so Win+V history skips it too; with the default `true` the dictation can be picked again from Win+V; the old text put back in step 5 is always marked private so it is not added to the history twice), sends the paste keys as virtual keys (`paste_chord`: Shift+Insert (the extended Insert key) when the focused exe is `putty.exe` or `mintty.exe` (`SHIFT_INSERT_TERMINALS`; they ignore Ctrl+Shift+V by default), Ctrl+Shift+V for the other terminals in `TERMINALS` (Windows Terminal, `wt`, `cmd`, PowerShell, `pwsh`, `conhost`, Alacritty, WezTerm), Ctrl+V (0x56) everywhere else; virtual keys, not letters, so it also works on Cyrillic, Greek, Hebrew and Arabic layouts). With `keep_clipboard` on it returns there; otherwise step 5 waits 1.0 s first (`PASTE_WAIT`; slow targets such as Electron apps under load, RDP or VMs read the clipboard late and would paste the old text if it were restored sooner);
  5. (with `background=True`, which `Engine.paste` passes, on a thread, so the dictation is done and the next press works as soon as the keys are sent, ENG-3; every later `paste_text`, `copy_selection`, copy-last and Quit first wait for it, `paste.wait_restored`, so a new dictation never takes the previous one for the old clipboard) restores the old clipboard (the whole snapshot, `clip_restore`, which adds the three private markers the snapshot does not already hold, so Win+V history and the cloud clipboard do not get the old item a second time; ENG-9) only when `keep_clipboard` is false (the default) **and** the clipboard still holds the dictated text, so something the user copied in the meantime is never overwritten. If no snapshot could be taken (clipboard busy, nothing copyable on it, more than 64 MB), only old text can be put back: when it could not be read, or reads as empty or non-text (`pyperclip` returns an empty string when the clipboard holds an image or files), nothing is restored and the dictation stays on the clipboard. GDI-handle formats (bitmap, metafile, palette) are not copied; the DIB formats stand in for images. A restore that fails is logged and never makes the paste fail. Trade-off: the dictation can stay on the clipboard for about a second.

  After a real paste (not a copy) `Engine.paste` calls `correction_watch.arm(text, cfg, notify)` (Learn from my corrections, below).
  `Engine.paste` returns True (pasted) or False (only copied, window changed or administrator window) and does not flash itself; `_process` flashes once, after the paste and the history step, green for a paste and red for a copy ([Result signal on the pill](#result-signal-on-the-pill)).
- History: one JSON line appended to `history.jsonl` unless `keep_history` is false.
- Timing (the Speed card): `Engine.start` makes a `timing.Timing` and marks `key_down` (start of `start`; at the time of the key event, which may have waited in the hotkey queue, ENG-10) and `rec_start` (the microphone stream running); `stop` marks `key_up`; `_process` runs the network steps inside `core.timing_scope(tm)` so `process_detailed` marks `stt_start`/`stt_done` and `process_text` marks `llm_start`/`llm_done` (a cleanup that fails still closes its mark); with streaming the engine marks `stt_start`/`stt_done` around `streamer.finish()` (only the last piece is left to send) and logs how many pieces there were and how many went while the user was speaking; `inserted` is marked right after the paste keys are sent (the restore of the old clipboard runs later, so it is not counted). The entry is saved as `timing` in the history line (`Timing.entry` plus `core.timing_info`: voice and cleanup model, host or "relay", whether the relay was used, plus `pieces` and the `upload` format). A Retry, a note and a dictation with history off are not timed. Nothing leaves the PC.
- Errors: `ApiError` (401 key rejected, 429 rate limit, other) and `requests.RequestException` add `(pcm, exe, note)` to `Engine.pending` and notify with "Your recording is kept: tray icon > Retry last dictation." `Engine.pending` is a list, oldest first, of at most 5 (`MAX_PENDING`, as Android's `PendingQueue`; a sixth drops the oldest): a later dictation, failed or not, never replaces or clears a kept one (ENG-1). `retry_last` re-runs `_process` on the oldest kept recording, with that recording's window as the paste target; its success removes only that entry, and a failed retry moves it to the back of the line. Any other exception in `_process` (an answer the server got wrong, a paste that raises because the clipboard is busy, a note that cannot be saved) also keeps `(pcm, exe, note)` and notifies "Something went wrong" or "Vox could not paste"; only a delivered text or a saved note clears it. Each of these failures also flashes a red ! on the pill; a saved voice note flashes the green check.

### Tray menu (pystray)

Open Vox (default action) · Retry last dictation (visible only while `pending` holds a recording; with more than one it reads "Retry dictation (N waiting)") · New voice note / Finish voice note · Start/Stop listening · Start a note / Stop listening with the note shortcut shown (only when `note_hotkey` is usable) · Keep listening: Note and Keep listening: Type (radio items, setting `listen_target`) · Recover listening session (only when a session left audio behind) · Start/Stop meeting notes · Run relay on this PC (a checkbox, ticked while `relay_run` is true) · Quit Vox. Icon colour follows state (`logo.draw`: idle blue, recording red, busy amber; keep listening uses the recording icon).

### Relay on this PC (`windows/relay_host.py`)

`Engine.relay` is a `RelayHost(data_dir, port, notify)` for the relay data folder `%APPDATA%\VoxRelay` (the relay's own default, so `python relay.py` and Vox share one relay) and the port from `relay_port` (default 8765; `relay_host.port_from` falls back to 8765 for an unusable value). The tray item "Run relay on this PC" (`Engine.toggle_relay`) flips `relay_run`, writes it into the settings file (it loads the file first, so settings the window saved meanwhile are kept) and starts or stops the host. `Engine.run` starts it at launch when `relay_run` is true. Changing `relay_run` or `relay_port` by editing `config.json` while Vox runs does not start or stop anything until the next Vox start or the next tray click (`relay_port` is read each time the relay is started). The tick mark shows the saved setting, not whether the relay process is running: the engine re-reads `config.json`, so the box follows the file, and it stays ticked when the relay did not start (busy port, launcher error) or ended by itself. Whether it runs is shown only by the notifications and `vox.log`.

- `relay_command(data_dir, port)` is `[Vox.exe, "--relay", "--data-dir", D, "--port", P]` in the frozen app and `[python, windows\vox_app.py, "--relay", ...]` from source. `RelayHost.start()` starts it once (a second call while it runs does nothing), `running()` asks the process, `stop()` terminates it, waits 5 s and kills it if it does not end. The launcher (`spawn_hidden`) gives it no console window and discards its output.
- **Never orphaned:** `Engine.quit` calls `relay.stop()` before `os._exit(0)`. The launcher also puts the child in a Windows job object with "kill on close", so if the engine is killed or crashes, Windows ends the relay with it. Stopping is a hard `TerminateProcess`: the relay's SIGTERM handler does not run on Windows. The relay keeps its data in SQLite, whose commits are atomic, so a killed relay should not leave a half-written note (inferred from SQLite's design; not tested by killing a relay mid-write).
- **Port check:** before starting, `start()` asks `port_busy(port)` (a TCP connect to `127.0.0.1:port`). If something already answers, for example a relay started by hand, it does not start a second one and says so. This is needed because the relay's server class (`ThreadingHTTPServer`) inherits `allow_reuse_address = 1` from `http.server.HTTPServer`, so it binds with `SO_REUSEADDR`, which on Windows lets a second relay bind a taken port without any error (checked on this PC on 2026-09-30: a second `relay.make_server` on the port of a listening one succeeded). The check does not cover a relay started by hand *after* Vox's one: `python relay.py` has no such check.
- **Messages (tray notifications):** the first time the relay ever starts on this PC (no `relay.json` yet) the notification says `tailscale serve --bg <port>` with the real port, which is how the phone reaches it; a busy port is reported as above; if the child ends within 10 s of starting the notification says so and points to `relay.log`; a launcher error (the exe could not be started) is shown with its message. The setting stays on in each case; untick the item to stop Vox trying.

### Config reload

`_watch_config` polls the modified time of `config.json` every second and reloads settings (and the hotkey) when it changes, but never while recording. This is how the window process changes engine behaviour. A load that could not open the file (`core.config_is_fallback()`, for example another process was replacing it) is not taken: the engine keeps its settings and tries again on the next tick, and a start on such defaults leaves `cfg_mtime` unset so the file is read at the next tick (issue 63).

### Quit (`Engine.quit`)

If a meeting is active it is stopped; if a keep-listening session runs it is ended and the engine waits up to 180 s for its note to be saved; if notes are still being written the engine waits up to 180 s; a dictation still being sent (`busy`) gets up to 120 s (`QUIT_BUSY_WAIT`, balloon "Finishing your dictation before quitting...", issue 63) and the old clipboard of the last paste up to 3 s to come back; then it stops the relay child process (if running), the tray icon and overlay, deletes `engine.json` and exits with `os._exit(0)`. Ctrl+C in the launching terminal calls `quit` too.

### Local control server

`Engine._serve`: `ThreadingHTTPServer` on `127.0.0.1` with a random port and a random 32-hex-character token, written with the process id to `%APPDATA%\Vox\engine.json`. Every request must be `POST` with header `X-Vox-Token`. Routes:

| Route | Body | Effect |
|---|---|---|
| `/meeting/start` | `{"uid", "manual"}` | Start meeting notes (calendar event by uid, or a manual title/attendees) |
| `/meeting/stop` | | Stop and start the final pass |
| `/meeting/status` | | Live status, transcript, questions and answers |
| `/meeting/catchup` | | "What did I miss?" summary of the last 10 minutes (exposed by `Api.meeting_catchup`; the current page does not call it) |
| `/meeting/ask` | `{"q"}` | Ask a question about the live meeting |

### Calendar watcher

Every 30 s, if a calendar is connected and no meeting is running, the engine looks for an event with attendees that starts within 60 s before to 180 s after now. `engine.calendar_action` decides: it starts notes only when `auto_notes` is on and you accepted the meeting (`my_status` "accepted", which is also the value when it is your own event or the calendar gives no answer); an invite you have not answered or marked tentative only shows a reminder. A meeting you declined is dropped by `gcal._parse_items` and `vcalendar.parse` (your `PARTSTAT` is matched by `my_email`) and never reminds. Each event is reminded once per run.

## Overlay (`windows/overlay.py`)

A small Tk pill at the bottom of the work area: live waveform while recording, bouncing dots while sending, a stop square with `Listening m:ss` (or a message such as "Paused: wrong window" or the time warning) while keeping listening (the pill is wider then, 230 px against 132; `overlay_mode.pill_clock` formats the time and the meeting timer uses it too), a timer while taking meeting notes, and for a moment after a dictation a green check or a red ! (next section). Created with extended window styles so it is click-through, never takes focus, has no taskbar button and stays on top. Tk runs on the main thread and polls `Engine.state`, `Engine.level`, `Engine.flash_kind` and `Engine.flash_until` every 33 ms (`FPS_MS`); other threads only set those fields. If the overlay fails to start the engine logs it and keeps running without it.

**Staying on screen.** The pill is a `Toplevel` of a hidden Tk root, so it can be rebuilt. While it is wanted, `Overlay._keep_up` re-asserts it every 0.5 s (`overlay_guard.ASSERT_SECONDS`), and in full whenever the state changes into `rec`, `listen` or `meet` even if the pill was already up (for example a recording that starts while the check mark shows). `_assert` probes the window (`IsWindowVisible`, `IsIconic`, `DwmGetWindowAttribute(DWMWA_CLOAKED)`, `GetWindowRect` against every monitor from `EnumDisplayMonitors`, the extended style, the frame handle, and Tk's `winfo_ismapped`), re-places it when the work area changed, and calls `SetWindowPos(HWND_TOPMOST, NOMOVE|NOSIZE|NOACTIVATE|SHOWWINDOW)`. When the probe found a problem it also shows the window without activating it, logs `overlay repair: ...` with the facts, probes again, and if the window is still hidden, minimised, cloaked or off-screen rebuilds it (`_rebuild`: a new window, which lands on the current virtual desktop; at most one every 10 s and 3 while the pill stays up; the focus is handed back if the new window took it). The checks are pure functions in `windows/overlay_guard.py` (tested in `tests/test_overlay_guard.py`); the orchestration is tested with Win32 and Tk faked in `tests/test_overlay_keep_up.py`. The Win32 functions are declared with argument and result types on private `WinDLL` objects (`overlay._api`, so `ctypes.windll.user32` elsewhere is unchanged), and failures are logged with `GetLastError`, once a minute per call. Not yet seen on a real screen: the `Toplevel` change, the repair and the rebuild were not run against a desktop (only the typed Win32 calls were tried, read-only).

**Watchdog.** The engine's daemon thread `overlay-watch` runs `Engine.check_overlay` every second. When the overlay's heartbeat (`Overlay.last_tick`, set every tick) is older than 3 s while the state is not idle, it logs every thread's stack once per stall. When `Engine.state` has not matched the engine's flags for 10 s (`rec` without `recording`, or a recording older than `MAX_SECONDS * 3 + STUCK_MARGIN`; `busy` without `busy`; `listen` without a session) it logs it and sets the state to idle, or calls `stop()` for a recording whose audio callback stopped. `Engine.set_state` records `state_since` for this. `overlay_mode` also never shows a flash whose deadline is more than `MAX_FLASH_SECONDS` (5 s) ahead. The same thread runs `Engine.check_hook`: when the keyboard listener stopped, or when the check itself ran more than `HOOK_STALL_SECONDS` (2 s) late (Python was frozen longer than Windows' 1 s low-level hook timeout, after which Windows removes a hook without telling anyone), it installs the hook again (`install_hook`, a new pynput listener) and logs a warning (ENG-2). Not run on a real desktop.

**Tray icon after an Explorer restart.** pystray 0.19.5 already handles the `TaskbarCreated` message (`pystray/_win32.py`, `_on_taskbarcreated` re-adds the icon, and the message is let through for an elevated process), so Vox adds nothing there.

## Result signal on the pill

`Engine.flash(kind)` makes the pill show **sent** (a green check, 0.7 s) or **error** (a red !, 1.8 s) and then go back to whatever the real state is. It is only a signal: `Engine.state` keeps its values (`idle`, `rec`, `busy`) and every error keeps its tray notification text, because the pill says *that* something failed, not *what*.

- **State:** `flash_kind` (`"sent"`, `"error"` or `""`) and `flash_until` (`time.monotonic()` deadline, `FLASH_SECONDS` gives the durations). `active_flash(now=None)` returns the kind while the deadline has not passed, else `""`; it never writes, so the Tk thread and the worker threads do not race on clearing it. `flash` does nothing when `Engine.overlay` is `None` (the pill failed to start), and raises `KeyError` for any other kind.
- **Cancelling:** `set_state("rec")` and `set_state("busy")` clear the flash, so a new recording or a retry replaces it at once; `set_state("idle")` keeps it (the result is flashed while the state is still `busy`, then the engine goes idle). A flash is also not drawn while the state is `rec` or `busy`.
- **Drawing (`overlay.py`):** each tick the overlay asks the pure function `overlay_mode(state, flash_kind, flash_until, now, meeting_active)` in `windows/overlay_mode.py` (no Tk, unit tested in `tests/test_overlay_mode.py`) what to show: `rec` or `busy` always; while idle a running flash (`sent` / `error`) instead of the meeting timer (`meet`), then the timer (or nothing, `None`) returns. The drawing code itself is Tk and is not unit tested. `_draw_sent` and `_draw_error` draw one line, and one line plus a dot, from coordinates worked out once in `Overlay.__init__`; each frame clears and redraws the canvas as before. The pill stays click-through. Not yet seen on a real screen: the canvas items were checked in a live Tk window and the shapes previewed from the same coordinates.
- **Green (`sent`):** a pasted dictation (`paste_text` returned `"pasted"`) and a saved voice note.
- **Red (`error`):** the dictation text only reached the clipboard (`"copied"`, together with "Copied; the window changed"); "Add your API key" or a bad server address; a microphone error; nothing heard; every send failure (`ApiError`, network error, an unexpected exception in `_process`).
- **Nothing:** a recording cancelled or shorter than 0.4 s, a dictation with no text, the "Cleanup did not work" notice (the words were still pasted, so that one is `sent`), and the informational notices (chosen microphone missing, meeting notes).

The phone does the same with `BubbleView.flash` ([05-android-app.md](05-android-app.md#result-flash-on-the-bubble)).

## Meeting notes (`windows/meeting.py`)

Class `Meeting`; started from the tray, the window or the calendar watcher.

- **Two recorders** (`_Source`, one thread each) with the `soundcard` library: `You` = default microphone, `Others` = loopback of the default speaker (what the PC plays). This is why your own lines are always labelled correctly. The Microphone setting does **not** apply to meetings (it uses the default microphone).
- **Live transcript:** each source cuts speech at natural pauses using a simple energy detector (30 ms frames, adaptive noise floor, pieces of 6 to 20 s, at least 0.5 s of speech), stores each speech piece in `you.raw` / `others.raw`, and queues it. One worker (`_transcribe_loop`) sends pieces to Whisper (`transcribe_segments`, at least 3.2 s apart to respect Groq's free-plan rate), filters hallucinations (`_good`, `_dedupe_repeats`), and merges lines (`_add`), dropping mic echo of the call audio.
- **Final pass** (`_final_pass`, when `final_pass` is true, default): re-transcribes the stored speech with `whisper-large-v3` in pieces up to 480 s and replaces the live lines.
- **Speaker naming** (`attribute_speakers`): asks the notes model to name `Others` lines from context and the attendee list; results show as "Name (likely)".
- **Notes** (`_notes`): the notes model (default `openai/gpt-oss-120b`, `notes_model`) writes Markdown with fixed sections (Summary, Discussion, Decisions, Action items, Open questions, Next steps, Who said what). Transcripts over 60,000 characters are condensed in parts first.
- **Saving:** `%APPDATA%\Vox\meetings\<id>\` gets `transcript.json` (written through a temp file and replaced), `notes.md`, `meta.json`, optional `my_notes.md`. `meta.json` is written right after `notes.md`, before the copy of the notes goes to `Documents\Vox Notes` (or `notes_folder`); if that copy fails (for example Controlled Folder Access) the meeting is still listed, with `export_error` in its meta, and control characters are stripped from the file name. Raw audio is deleted afterwards unless `keep_audio` is true, whatever the export did, or unless the transcript does not cover it: `_finish` applies the recovery rule (`_covers_audio`, at least `MIN_WORDS_PER_SPEECH_SECOND` words per second of recorded speech), and a meeting that falls short keeps its `*.raw` files, gets `incomplete: true` in `meta.json` and a line in its notes (issue 49). There is no button to transcribe such a meeting again: the audio is plain 16 kHz PCM in its folder. The log names the meeting only by its id ("saved, exported" / "not exported", the error type of a failed export), never by its title or the export path.
- **Meeting ids:** a saved meeting's folder is named like its id, `YYYYMMDD-HHMMSS`. Every function that takes an id (`read_notes`, `delete_meeting`, `detail`, `save_my_notes`, `set_done`, `rename`, the bridge's `meeting_open`) first checks it with `meeting._folder_of`: anything else, or a folder that does not sit directly inside `meetings/` (a link pointing elsewhere), raises `ValueError`, and the bridge methods answer `False` or an empty name instead. The notes copy in Documents is named with `meeting.export_name` (control characters and `/ \ : * ? " < > |` become spaces, at most 60 characters).
- **Audio frames:** the 100 ms blocks of a recorder are cut into 30 ms frames with the remainder carried to the next block (`meeting._frames`); before, 160 of every 1,600 samples were dropped, so a tenth of the meeting audio was missing and piece times drifted.
- **Recovery:** a meeting cut off by a quit (the 180 s limit), a crash or a shutdown has a live transcript and raw audio but no `meta.json`. `meeting.recover_unfinished` runs once at the start of `Engine.run`: for every folder named like a meeting id without a `meta.json` it writes `notes.md` (the live transcript under "Unfinished meeting") and a `meta.json` with `unfinished: true`, so it is listed, and removes the `*.raw` audio only when the live transcript covers it (at least `MIN_WORDS_PER_SPEECH_SECOND` words per second of recorded speech) and `keep_audio` is off; an empty or partial transcript keeps the audio, adds `incomplete: true` to `meta.json` and says so in the notes. The notes of such a meeting are not summarised.
- **Ask:** `ask_live` (during a meeting), `ask_meeting` (one saved meeting), `ask` (searches all meetings by keyword score and sends the best four to the model).
- **Concurrency:** `ctl` lock serialises start/stop; `lock` guards `entries`/`qa` for status and the final-pass swap.

All model calls go through `core.post_with_retry` to the configured server. Details of each prompt are in the constants at the top of `meeting.py`.

## Calendar (`windows/gcal.py`, `windows/vcalendar.py`)

- `vcalendar.fetch(cfg)` returns `{"events", "error", "fetched", "source"}` for 12 h ago to 7 days ahead, cached 5 minutes in `calendar.json`; a failed fetch keeps the events of the last good fetch of the same source and is tried again after about 30 seconds (it used to cache an empty list for 5 minutes, which hid the next meeting from the watcher). Titles, attendee names and the organizer are one line of at most 120, 80 and 80 characters (`vox_core.one_line`) and a meeting has at most 30 attendees. Source is Google (if connected) or the ICS link in `calendar_url` (`webcal://` accepted). The secret link is never written to `calendar.json` (the `source` is `ics:` plus a short hash of it) or to the log: a failed fetch stores only "Calendar server answered 404" or "Could not reach <host> (<error type>)", and clearing the link deletes `calendar.json`.
- `gcal`: OAuth 2.0 for desktop apps with a loopback redirect and PKCE; scope `calendar.events.readonly` plus `openid email`. Needs a `google_client.json` (from a Google Cloud project) next to the app, bundled at build time from the `GOOGLE_CLIENT_JSON` secret, or in `%APPDATA%\Vox`. Without it the Google button is unavailable and the ICS link still works. Tokens are in `%APPDATA%\Vox\google_token.json` (`refresh_token` and `access_token` protected by the Windows login like the API key; `_load_token`/`_save_token`; a plain file from an older Vox is protected on the first read; a file that cannot be opened, for example from another Windows user, makes `_access_token` say "Connect again in Vox > Notes", see [09-security-privacy.md](09-security-privacy.md)).
- All-day events and cancelled events are skipped; attendees exclude you, rooms and declined guests.

## Syncing voice notes

`Engine.__init__` creates a `sync.SyncWorker`; `run` starts it (it syncs at once), `quit` stops it, and saving a note calls `self.sync.trigger()`. The control server has `/sync/now` (trigger, answer with the status) and `/sync/status` (`enabled`, `running`, `last_run`, `last_ok`, `error`, `pushed`, `pulled`). The window calls them through `Api.sync_now` and `sync_status`; `Api.note_edit` and `note_delete` ask the engine to sync after a change, and `Api.sync_test` checks an address and token without saving them. `Api.get_devices` returns `sync.devices_for_ui(config)`: `{ok, error, devices: [{name, this, state, ago}]}` from the relay's `GET /devices` (`sync.fetch_devices`, needs only the saved address and token, not the notes switch); a failure is an empty list and the reason ("Cannot reach the relay (is Tailscale running?)", "The relay refused the token.", "This relay is too old to list devices."). The rows come from the pure `sync.devices_view(devices, now, my_name)`: state `active` under 10 minutes since the relay last saw the device, `recent` under a day, else `old`; "this device" when the name is this PC's `sync.device_name` (or the `?` spelling Android sends); the order is the relay's (newest first). Settings has a **Devices on my relay** card under the relay settings (Refresh button, a green/blue/grey dot per state, a "this device" badge, "No device has synced yet", the failure reason in red). It loads when Settings opens or the address or token changes only while sync or "Use my relay as the AI server" is on, and always on Refresh or after a successful Test (otherwise it says "Press Refresh to ask the relay..." and makes no request); with no address or token it says what is missing and makes no request. The list markup is `devicesHtml` in `ui-shared/common.js`. Settings has a **Sync between devices** block inside the Privacy section (switch, relay address, token, device name, Test) and the Voice notes page shows "Synced 2 min ago" or the last error, with a Sync now button. How a run works and why: [decisions/0022-sync-client-dirty-flag-and-cursor.md](decisions/0022-sync-client-dirty-flag-and-cursor.md). A note that the relay refuses for good (`SyncError.permanent`: a 4xx other than 401, 403 and 429, for example a bad note id) is skipped for that run and counted in the result (`error` says "1 note could not be sent: ..."); it stays dirty and is tried again once per run, and the other notes, the pull and the profile still sync. Any other failure (no network, 401, 403, 429, 5xx) stops the run. Notes made on this PC carry the device name (`sync.device_name`). **Test connection** (`Api.sync_test` calls `sync.test_relay`, which asks `GET /health` and lets the pure `sync.relay_check` decide) answers `{ok, reachable, token_ok, device_name, relay_version, notes, message}`: `ok` means a relay answered and took the token, `reachable` that a relay answered at all (a 401 or 403 is a relay's own refusal), `token_ok` that the token was accepted (a 403 means it was), `device_name` the name this PC sent (the relay lists it under that name, so the Devices card shows it after a good test), `relay_version` the relay's version when it looks like one. The `message` is unchanged ("Connected. The relay holds N notes."); the page adds three rows under it (Relay, Token, This device) with the shared `relayCheckRows`, and clears them when the address or token is edited. A good Test also saves the typed address and token and refreshes the Devices card. The card **How to set up the relay** (`#relay-steps`, collapsed) sits under the relay settings; its text is `ui-shared/relay-steps.txt`, written into both pages by `tools/sync_ui.py`, and each step with commands has a Copy button (`api().copy`). The tray notification that appears when Vox first starts its own relay names the same `tailscale serve` command and points at this card.

### Profile sync

After the notes, `sync.sync_once` calls `sync_profile`: it reads the relay's profile, merges it field by field with this PC's `config.json` (the side that changed since the last sync wins; if both changed, the relay's value wins; on this PC's first sync, with no snapshot yet, a blank value on the relay, an empty text or list, never replaces a value set here), saves what came in, and writes the merged document back with `If-Match` when it differs (a refused write is retried up to three times). The shared fields are `user_context`, `dictionary`, `people`, `default_style`, `cleanup`, `language` and `my_cleanup_rules`; with **Also share my provider settings and API keys** (`relay_sync_keys`) also the provider, models and keys. Keys leave the relay only when this PC switches the setting off after having sent them (`profile_keys_sent` in `sync_meta`); a PC that never sent keys leaves other devices' keys alone. The sync state belongs to one relay: when `relay_url` changes (`sync.follow_relay`, `relay_origin`) the cursor and profile state are reset and every note and delete marker is sent again (`profile_keys_sent` is kept: the new address may be the same relay under another spelling, and a different relay without keys just clears it at its first sync). An install with no saved `relay_origin` and the keys switched on sets `profile_keys_sent` when the first sync records the address, so keys that were already on the relay before the flag existed are taken off when switched off. Per-app styles, hotkey, microphone and the relay settings never sync. The engine triggers a sync whenever it reloads changed settings. See [decisions/0023-profile-sync-three-way-merge.md](decisions/0023-profile-sync-three-way-merge.md).

## Keep listening (`windows/listen.py`, `windows/session.py`)

A double press of the dictation shortcut (or the tray, or the note shortcut) calls `Engine.start_listening`, which checks the settings (`_ready`), opens a `SessionBuffer` (the audio on disk), creates a `listen.Listening` and opens the microphone with its callback (`_open_mic`); `Engine.listening` is set and the pill state is `listen`. The callback only queues bytes. The feed thread writes the buffer and gives the audio to the pure `ListenSession`, which cuts it at pauses (`Segmenter`, 3 to 20 s) into pieces; the stt thread transcribes one piece at a time with `streaming.piece_text` and answers the session; for the Type target a type thread cleans each piece (`process_text`) and pastes it with `Engine.paste` while `session.same_target` holds. Esc calls `Listening.cancel` instead (see Hotkey behaviour): nothing more is sent and no note is saved. The end (a double press, the stop phrase, the tray, the note shortcut, 60 minutes, or a microphone that sent nothing for 5 s) calls `Listening.stop`: the microphone is closed, the rest of the audio is sent, and `_finish` saves the note. Note target: the whole text is cut by `chunk_text` and cleaned chunk by chunk (the fidelity guard applies to each, so a failed chunk falls back to its spoken words) and saved with `Engine.save_note`. Type target: only what was not typed is saved. The audio file is removed after a clean end and kept after a failure; the tray's "Recover listening session" (`recover_listening`, offered by a balloon at startup) replays it into a Note session. `Engine.listen_state("busy")` makes the hotkey and the tray wait while it saves. Nothing is added to the history. The marks `seg_end` and `seg_text` (see [06-pipeline.md](06-pipeline.md)) time each piece. Not run with a real microphone or server; the checklist is in [specs/p9e-keep-listening.md](specs/p9e-keep-listening.md); the reasons in [decisions/0032-keep-listening-pieces-two-targets-crash-safe-buffer.md](decisions/0032-keep-listening-pieces-two-targets-crash-safe-buffer.md). Android has no keep-listening (out of scope for this round).

## Learn from my corrections (`windows/correction_watch.py`, `windows/autolearn.py`)

`Engine.paste`, after a real paste, calls `correction_watch.arm(text, cfg, notify, quiet)`; `quiet()` is true while Vox records or a keep-listening session runs, and then the thread reads nothing (ENG-2). With `auto_learn` on, the module's `Watcher` (made on first use, only when `make_provider` finds Windows and pythonnet) arms an `autolearn.Watch` with the foreground window handle and starts a daemon thread `vox-autolearn`. Every 2 s (`POLL_S`) the thread compares the foreground window with the armed one and, only when it is the same, reads the focused control's text with `UiaProvider` (the .NET `System.Windows.Automation` classes through pythonnet, loaded on the first read in that thread: `TextPattern.DocumentRange` up to 20,001 characters, else `ValuePattern.Value`; a password control is never read). Only .NET methods reach the other app: `GetCurrentPropertyValue` (`IsPasswordProperty`, `ValueProperty`), `GetCurrentPattern`, and reflection (`PropertyInfo.GetValue`) for `FocusedElement` and `DocumentRange`. pythonnet holds the GIL while a property getter runs, so a slow app answering a property froze all of Vox: the keyboard hook, the audio callback and the pill (ENG-2). `pythonnet` is pinned in `windows/requirements.txt` because this depends on its version. The watch decides when to analyse and when to end (see [06-pipeline.md](06-pipeline.md)); a control without text ends it and logs "auto-learn: control exposes no text" once per run. When the watch ends the thread ends. New pairs are added to `dictionary` and `learned_log` in `config.json` (`autolearn.apply_learned`) and announced with the tray balloon "Learned: wrong -> right" (`notify(..., private=True)`, so the words are not logged; the log says "auto-learn: learned N corrections"). A new paste re-arms the watch after a final check of the old one. The engine reloads the changed `config.json` as for any other change. Not run on a real desktop: see [specs/p9i-auto-learn.md](specs/p9i-auto-learn.md) for the checklist.

## Improve my cleanup (`windows/improve.py`)

The Settings card asks a stronger model to propose dictionary words, replacements and cleanup rules from the person's own saved dictations. The pure module `improve.py` selects the history pairs (the newest that fit 40,000 characters, handed over oldest first), estimates the cost, builds the JSON request, reads the answer tolerantly with caps, applies ticked items to the config as a version and reverts a version; the window's `Api` (`improve_state`, `improve_run`, `improve_apply`, `improve_revert`) is the only caller of the server (`improve.ask` over `core.chat_text`, to the cleanup server or the relay). **A run sends the transcripts only after the confirm step and its Send button**, and `improve_run` refuses when the confirmed count and characters do not match the history. The proposal lives in memory inside the `Api` object and Apply works only on it; About you suggestions are never applied. The engine's hourly `check_improve_reminder` only shows a tray message (`improve_remind`). Learned rules are the setting `my_cleanup_rules` (put into the cleanup prompt, synced to the phone with the profile). See [specs/p9f-improve-my-cleanup.md](specs/p9f-improve-my-cleanup.md) and [decisions/0033-the-improvement-run-sends-transcripts-only-on-an-explicit-button.md](decisions/0033-the-improvement-run-sends-transcripts-only-on-an-explicit-button.md). Not run against a real model.

## Long recordings in pieces

`Engine.start` creates a `streaming.StreamingStt` (when `stream_stt` is on) and starts its thread; it cuts at the first pause after 6 s (`streaming.MIN_SECONDS`) and at the latest after 20 s (with no pause by then, at the quietest 30 ms frame of the last 2 s, not in the middle of a word: `Segmenter._forced_cut`), so any recording longer than about 7 s with a pause in it is sent in pieces while it is spoken (before task B4 only from 12 s on); the microphone callback `_audio` feeds it (a queue put only). `stop` hands it to `_process(pcm, exe, note, streamer)`, which calls `streamer.finish()` in the processing thread: a text means the recording was cut and transcribed in pieces, so only `core.process_text` runs (cleanup once on the joined text); `None` means it was too short to cut, a piece failed or it timed out, so `core.process_detailed` transcribes the whole recording as before; after a failed piece, though, `streamer.partial()` keeps the text of the pieces before it and only the rest of the recording is sent (`core.transcribe_rest`, ENG-7). `cancel`, a too-short or silent recording and a microphone error cancel the streamer. The whole recording stays in `Engine.pending` for Retry. See [decisions/0024-stream-long-dictations-in-pieces.md](decisions/0024-stream-long-dictations-in-pieces.md).

**Warm microphone (setting `warm_mic`, off by default).** With it on, `Engine._sync_warm` (run once a second by the config thread while no recording is going on) keeps one `sounddevice` input stream open on the chosen microphone (`_open_warm_stream`; a missing chosen microphone is left to `_open_mic`, which says so). `windows/warm_mic.py` holds the parts that do not need a microphone: `RingBuffer` (the last 400 ms of 16-bit audio, in memory only) and `WarmMic` (opens, reopens on a device change or a dead stream, retries a failed open at most every 30 s, one notification per failure spell). While idle, the audio goes only into the ring. At key-down `_begin_capture` calls `WarmMic.attach`: the held audio is fed first to `_audio` (so it reaches `chunks` and the streamer in order, `_preroll` remembers its size so `stop` does not count it towards `MIN_SECONDS`), then every live block; `_close_stream` calls `detach` instead of closing, and the ring fills again. If the stream is not ready, or is being opened at that moment, the normal `_open_mic` path runs, so nothing changes for the user except the missing pre-roll. The stream is closed when the setting is turned off, when `input_device` changes and in `quit`; `_refresh_audio` does not rebuild PortAudio's device list while it is open. Keep listening and meetings do not use it. Windows shows the microphone-in-use icon all the time while it is on. Tests: `tests/test_warm_mic.py` (pure), `tests/test_engine_warm_mic.py` (fake `sounddevice`).

Every upload of a dictation (the pieces, the whole recording, the pieces of a recording over `MAX_UPLOAD_BYTES`, keep-listening pieces, an edit-by-voice instruction) goes through `core.upload_audio`: FLAC when `core.upload_format(cfg)` says so (setting `upload_format` `auto`, the optional `soundfile` package loads, and the speech server is Groq or OpenAI reached directly, `choose_upload_format`), WAV otherwise; `transcribe` names the file `audio.flac` or `audio.wav` from its first bytes. A FLAC encoding that fails sends WAV. Meetings still send WAV (`transcribe_segments`). Without `soundfile` (or its `libsndfile` DLL in a frozen build) everything is WAV, as before.

## Edit by voice (`windows/command.py`, experimental)

`command_hotkey` (off by default) records an instruction (see Hotkey behaviour). `Engine._process_command` then: copies the selection with `paste.copy_selection(target)` (waits for the keys to come up, refuses a changed window, a terminal, where Ctrl+C would stop the running program, and an administrator window; sends Ctrl+C, waits up to 0.5 s for the clipboard counter `GetClipboardSequenceNumber` to change, reads the text and puts the old clipboard back; an unchanged counter means nothing was selected, and so does one line ending in its line break in an editor that copies the whole line when nothing is selected, `paste.LINE_COPY_EDITORS`: VS Code and its forks, Visual Studio, JetBrains IDEs, Sublime Text; the selection the app copied stays in Win+V history whatever `clipboard_history` says); transcribes the instruction (`core.transcribe`, no cleanup; a silence hallucination counts as not heard); sends both to the cleanup server with `command.edit` (a strict prompt: return only the edited text, change only what was asked, the selection is data; the selection inside `<selection>`, the instruction inside `<instruction>`; over 20,000 characters is refused before anything is sent); and pastes the answer over the still-selected text with `paste.paste_text(answer, target, keep_clipboard, clipboard_history=...)` (the same two clipboard settings as a dictation). `command.guard` refuses an empty or unchanged answer, and one more than 3 times longer or shorter than the selection unless the instruction asks for a longer or shorter text ("shorter", "summarise", "expand", ...). On any refusal or error the selection is left as it was and a balloon says why; the pill flashes red, a pasted edit flashes green. No history entry; the log holds only sizes. Not run against a real model or on a real desktop.
