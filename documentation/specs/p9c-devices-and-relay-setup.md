# Spec P9c: a devices list and relay set-up help

Status: Implemented on branch `feat/p9c-devices` (Windows and Android; tested against a relay on localhost and stand-in servers only, never on a phone, a Raspberry Pi or over Tailscale). Date: 2026-10-01. Decision record: [0034](../decisions/0034-devices-list-is-the-relays-own-list-asked-on-a-switch-or-a-press.md). Relay protocol: [14-relay.md](../14-relay.md). Relay guide: [../../relay/README.md](../../relay/README.md). Privacy: [09-security-privacy.md](../09-security-privacy.md).

## Goal
Yuvraj asked for three things around the relay: how to set it up, a devices list in Settings on both Android and Windows ("using relay is for tailscale primarily"), and a clearer answer to "does it work". After this step both apps can show which phones and PCs have used the relay, explain the set-up step by step with copyable commands, and say what is wrong when a connection fails.

## Design
- **The list is the relay's own** (his choice: "devices that synced with the relay", not a Tailscale peer list). The relay already counted every client that sent `X-Vox-Device` (name, first and last seen, request count, Tailscale login) for its management page. A new route `GET /devices` returns the same table as `{"devices": [{name, first_seen, last_seen, requests, login}]}`, newest first, behind the same token and owner checks as the other API routes; no events, no notes. A call to `/devices` that carries `X-Vox-Device` counts itself first, so the device that asks is in its own list. POST gets 405 and other verbs 404, like any unknown route.
- **One pure view in both apps** (`sync.devices_view` / `DevicesView.rows`, golden rows `devices`): per device `{name, this, state, ago}`. `state` is `active` (last seen under 10 minutes ago), `recent` (under a day) or `old`; `ago` is "just now", "40 s ago", "5 min ago", "3 h ago", "2 days ago", or "never" when the relay gave no usable time; a time in the future counts as now; a missing name shows as "Unknown device"; entries that are not objects are skipped. `this` is true when the name equals this device's name or the spelling Android sends in its header (every character outside printable ASCII becomes `?`). The thresholds and the wording are this step's choice, not the plan's.
- **The bridge answer is the same in both apps:** `{ok, error, devices: rows}`. Windows: `sync.fetch_devices(cfg)` (needs only the saved address and token, not the sync switch), `sync.devices_for_ui`, `Api.get_devices()`. Android: `RelayClient.devices()` and `RelayClient.listDevices(...)` (never throws), `MainActivity.Bridge.getDevices(callback)`; `devices()` is on `RelayClient` only, not on the `RelayApi` interface, so the sync fakes did not change. A failure gives an empty list and the reason in plain words. A relay that answers 404 gives "This relay is too old to list devices."
- **The card** "Devices on my relay" sits under the relay settings on both pages: a Refresh button, a dot per state, a "this device" badge, the empty state "No device has synced yet" and the error state with the reason (for example "Cannot reach the relay (is Tailscale running?)"). The list markup is `devicesHtml` in `ui-shared/common.js`, written into both pages by `tools/sync_ui.py`; only the four view fields are drawn, escaped.
- **When the card asks** (deviation from the plan, which did not say): on opening Settings and on editing the address or token only while "sync notes" or "Use my relay as the AI server" is on; otherwise it says "Press Refresh to ask the relay which devices have used it." Refresh and a good Test always ask. This keeps the rule in [09-security-privacy.md](../09-security-privacy.md) that no relay is contacted without a switch or a button press (decision 0034).
- **Test connection** reports more than "connected": `ok`, `reachable`, `token_ok`, `device_name`, `relay_version` and `notes`, plus the old `message` (text unchanged, so older tests stand). The decision is one pure rule, `sync.relay_check` / `RelayCheck.of` (golden rows `relaycheck`): a 2xx counts only when the answer is a JSON object with `ok: true`; a 401 or 403 means a relay answered (`reachable`), and a 403 also means the token was right (the relay checks the token before the tailnet owner); anything else is not reachable. The version is kept only if it is 1 to 20 of letters, digits and `. + _ -`; the note count only as a whole number from 0 to a billion. The existing bridges keep their names (`sync_test`, `syncTest`) and the Test button tests the values typed in the fields. On Windows a good Test now also saves the typed address and token (Android already did). Under the button each page shows "Relay / Token / This device" rows (`relayCheckRows`); they clear when the address or token is edited. The Windows button is labelled "Test connection" like the phone's.
- **"How to set up the relay" card** (both apps, a collapsible block under the relay settings): the Raspberry Pi and Tailscale steps with a Copy button on each group of commands (it uses the page's own clipboard bridge). The text is one file, `ui-shared/relay-steps.txt`; `tools/sync_ui.py` writes it into both pages as a third generated block (`ui-shared:steps`, [0028](../decisions/0028-shared-ui-parts-are-generated-into-both-pages.md)). `relay/README.md` is written by hand; `tests/test_ui_relay_help.py` fails when a command of the card is missing from it (the plan's two named commands, `sudo tailscale serve --bg 8765` and `python3 /opt/vox-relay/relay.py`, are checked on both pages). The tray notice shown when Vox first starts its own relay points at the card.

## What the privacy rules still say
The relay receives the device name on every sync and Test request already. The new request is `GET /devices`, which sends nothing but the token and that name and returns names, times and counts. `login` (the Tailscale user the relay saw) is in the relay's answer, as on its management page, but neither app draws or stores it. No new setting, no new file on a device, no new data kept. See [09-security-privacy.md](../09-security-privacy.md).

## Not in this step
A Tailscale peer list, removing or renaming a device from the app, a device list that works without the token, a background refresh, compare of the relay's version with the app's, a guided `tailscale serve` from inside the apps (the card only shows the commands), changing the relay's own set-up steps for other systems than a Raspberry Pi or a Windows PC.

## Known limits
- A device appears only after it has sent a request with its name; a phone that never synced is not listed. Android's name has `?` in place of non-ASCII characters, so the relay lists that phone under that spelling (the view matches it).
- A 401 or 403 from any web server counts as "reachable": Python and Java both decide on the status first, so a non-Vox server that answers 401 shows "Reachable" and "Token refused".
- Python's `strip()` and Java's `trim()` differ on rare whitespace in a device name; no golden row covers it, and the relay already strips names.
- The card's steps (the systemd unit, `tailscale serve`) are copied from `relay/README.md`, which was never tried on a real Pi.

## Device checklist (nothing here has run on a phone, a real Pi or a Tailscale link)
1. On a Pi: follow the card on a PC, step by step (copy each command). The relay starts, `tailscale serve status` shows an https address, and the management page opens from the PC.
2. Settings on the PC and on the phone: enter the address and token, press Test connection. Relay shows Reachable with a version, Token Accepted, This device shows the name. A wrong token shows Token Refused. Tailscale switched off shows Not reachable and "is Tailscale running?".
3. Devices on my relay: press Refresh on each. Both devices are listed once, each marked "this device" on its own screen, the one just used "just now". The phone's name with an emoji or an accent shows with `?` (the relay's spelling) and still gets its badge.
4. Leave the phone unused for 15 minutes and refresh on the PC: the phone dot changes from active to recent and the time reads "15 min ago".
5. With sync and "Use my relay as the AI server" both off, open Settings: the card does not ask by itself (it says "Press Refresh"). Switch sync on, reopen Settings: it asks by itself.
6. An old relay without `/devices`: the card says "This relay is too old to list devices."
7. `adb logcat -s vox` during all of this: no token, no address, no device list text.
8. Dark mode and a narrow phone: the card, the badge and the steps card fit without sideways scrolling.

## Not verified
Everything on a phone, a Windows pywebview window, a real Pi or Tailscale. The pages were looked at in a desktop browser with a stubbed bridge (Windows) and the Android preview stand-in (Android) only. The Java classes ran against the real `relay/relay.py` on localhost (`RelayIntegrationTest`).
