# 12. Known issues and roadmap

State of the code, honestly. Update this page when you fix or discover something. Items are grouped by kind, roughly most important first.

## Known issues

### Behaviour and correctness

| Issue | Detail |
|---|---|
| `ACTION_SET_TEXT` rewrites the whole field (Android) | `VoxAccessibilityService.insertText` sets the complete new text, so rich text formatting can be lost and typing during insertion can race. The clipboard-paste path is only a fallback. |
| Microphone setting is ignored by meeting notes (Windows) | `meeting.py` records the default microphone through `soundcard`; only dictation uses `input_device`. |
| Failed Windows dictation audio lives in memory only | `Engine.pending` is lost when Vox quits (Android keeps a file until sent or cancelled). |
| Spoken "new line" false positives | When cleanup did not run, a phrase like "a new line of code" becomes a line break. This is a deliberate trade-off. |
| Fidelity guard limits | Counts words, not meaning: a one-word change that flips the meaning in a long text passes. Standard strength has no absolute cap, so a 1,000-word dictation can lose a few percent unseen (Light caps missing words at 12). A cleanup that turns a spoken list into numbered items and drops `first`, `second`, `third`, and a translation all count as lost words, so they fall back to the raw words. Also not understood: fractions (`a quarter`, `quarter past three`), `out of` (`three out of five` -> `3/5`) and a digit before a scale word (`2 million`); they fall back to the raw words too. The thresholds were tuned on written examples, not on real model output. Light is the default strength (the Settings row "Cleanup strength" switches to Standard), so a model that is good at removing fillers is rejected more often than before, not less. The capitals the fallback adds are a plain rule on `.`, `!`, `?` and line breaks: after an abbreviation such as `e.g.` the next word also gets a capital. See [specs/p9a-cleanup-keeps-my-words.md](specs/p9a-cleanup-keeps-my-words.md). |
| Note rules differ slightly between platforms | `notes._tags` (Windows) has no limit on the number of tags, while `NoteLogic.cleanTags` (Android) keeps at most 20 (the relay's limit); both remove double quotes; tag clean-up has no golden rows. "Word" and "space" in `auto_title` and `fts_query` follow each runtime's Unicode tables (Python 3.13: Unicode 15.1; Android's Java: whatever the phone's version has), so letters added in a newer Unicode version can count as words on one side only. The whitespace set is written out in `NoteLogic` and matches Python's `str.isspace()` exactly. |
| A sideloaded APK cannot avoid the install warnings | Android's "Restricted setting" for the accessibility service (Android 13 and newer) and Play Protect's "App blocked" or "unknown app" prompt come from how the APK is installed, not from the manifest. The Install help card (Settings, System) lists the taps and the adb way; the real fixes are Google Play (closed testing) or an app store such as F-Droid, none of which is set up. Unconfirmed: whether the restriction returns on an update, and what Play Protect shows for adb installs ([specs/p9g2-install-safety.md](specs/p9g2-install-safety.md)). |
| Android `targetSdkVersion` is 34 | The research recommends 35 or 36 (Play Protect warns when the target is more than two levels below the phone, so Android 17 would warn). It stays at 34 because the sources compile only against `platforms/android-34`; the steps to raise it (new platform in CI and the scripts, behaviour-change review, a device pass) are in the p9g2 spec and [decisions/0035](decisions/0035-sideload-warnings-are-explained-not-engineered-away.md). |
| Android note mode is unchecked on a phone | The note bubble, the "Record note" notification, the quick settings tile and the save path in `DictationService` only compile and have read-through review; the microphone service starting from each entry point on Android 14 and 15, the tile and notification actions, the Stop button, and a note landing in the store have not been tried on a device; the same goes for the note bubble that comes up by itself while a note records (timer, tap to save, flash, then gone; checklist in [specs/p9g-note-bubble.md](specs/p9g-note-bubble.md)). The ongoing notification is not restored after a reboot until the app or the accessibility service starts (no boot receiver), and on Android 14 a user can swipe it away. |
| Android note mode: lifecycle limits | Four edges are known and not fixed. (1) The quick settings tile is an active tile (`ACTIVE_TILE`) and the service asks it to refresh when a note starts or ends, but if the app's process is killed in the middle of a note nothing tells the tile, so it can stay ACTIVE until it is next listened to. (2) The cancel race is narrowed, not closed: `saveNote` re-checks that its job is still the current one right before `NotesStore.add`, but a cancel that arrives between that check and the write still saves the note. (3) `TrampolineActivity.finishNow()` is called as soon as `startRecording` returns, while the `AudioRecord` starts a few milliseconds later on its own thread; this relies on the microphone foreground service having been started while the trampoline was visible, and if a device records silence after the trampoline closes the fallback is to move `finishNow()` to the first audio frame (see the device checklist in [specs/p6-android-note-mode.md](specs/p6-android-note-mode.md)). (4) A double tap on the bubble while the service is not running opens a second trampoline; the second `startRecording` returns at once because the state is no longer idle. |
| Android notes database is unchecked on a phone | `NotesStore` needs Android's SQLite, which the local Java tests cannot run, so it is only compile-checked and read against `windows/notes.py`. Whether the phone's SQLite has FTS5 (otherwise search falls back to `LIKE`) and that both search paths, edit, delete and the sync calls work has to be tried on a device. |
| Meeting hallucination list differs from dictation's | `meeting.HALLUCINATIONS` is wider than `vox_core.SILENCE`; both exist separately. |
| `Api.meeting_catchup` and `/meeting/catchup` exist but the window never calls them | `.catchup` CSS in `ui/index.html` is also unused. |
| Windows history is unbounded | `history.jsonl` only grows; the window shows the newest 300. Android keeps 500. |
| New screens are unchecked on a phone and a Pi | The Windows screens were looked at by a contributor on a Windows laptop (2026-09-30, "looks good", details not recorded). | Android speed work has not run on a phone | The pieces sent while recording (`StreamingStt` in `DictationService`), the m4a upload (`AudioUpload`: `MediaCodec` and `MediaMuxer`), the warm-up on a bubble touch, the `AudioRecord` made on the recording thread and the shorter timeouts are tested only as pure rules (`LatencyTest`, `SegmenterTest`, `StreamingSttTest`, golden rows) and compile-checked. | Android relay sync: unencrypted secrets | The relay token (`relay_token`) and the API keys sit in SharedPreferences in plain text, like the existing API key (see [09-security-privacy.md](09-security-privacy.md)); the code never logs them and sends the token only to the relay's own address. | Android relay sync: known limits | The phone syncs only while the app's process is alive: the first kick (the app opening, the dictation service starting, a settings save) starts the 90 s tick, and the tick keeps running for as long as the process lives, which includes `VoxAccessibilityService` (it runs in the same process), so it may go on after the app is closed; when the system ends the process nothing syncs until the next kick. A saved note does trigger a run (`SyncWorker.start` registers one `NoteEvents` listener per process), but only if the process is alive, and the listener exists only after the first kick in that process. There is no boot receiver and no background scheduler (`WorkManager` or an alarm), on purpose. A note the relay refuses for good is tried once in every pass and reported each time until it is edited or deleted. The first time a device syncs against a relay that already has a profile it has no snapshot to compare with, so a setting both sides have is taken from the relay: a phone that already had its own dictionary loses it to the relay's, unless the relay's value is blank (an empty text or list is only the other device's default and never replaces a value here; the same on Windows, see [decisions/0023-profile-sync-three-way-merge.md](decisions/0023-profile-sync-three-way-merge.md)). Comment lines in the dictionary are not shared. A Windows server address such as `http://localhost:11434` arrives as it is and does not work on a phone. `llm_reasoning` is not shared with the phone (it always behaves as `auto`). The relay cuts note text at 100,000 characters without an error, so a longer note reaches other devices shortened while the phone keeps all of it. |

| Relay proxy: framing refusals do not drain the body | A 411 (chunked or missing `Content-Length`) or a 400 (repeated or malformed `Content-Length`) is answered without reading the body, unlike 413 and 503 which drain up to 5 MB first. | Relay proxy: `_scrub` covers the body only | If an upstream echoes the key, it is replaced with `***` in the body; the copied `Content-Type` and `Retry-After` headers are not scrubbed. Keys shorter than 8 characters are not scrubbed at all. |
| Relay proxy: a slow uploader can hold a slot | A slot is held while the client sends its body; a token holder that sends one byte every 29 s can keep one of the four slots (each read waits at most 30 s). Single-user token model, not mitigated. |
| Relay proxy: `_open_socket` and abandoned resolver threads | `socket.socket()` is created outside the `try` in `_open_socket`, so if it fails for one address (for example IPv6 not available) the remaining addresses are not tried and the call ends there (inferred from the code: the error is an `OSError`, which the caller turns into the fixed 502). A name lookup that never ends is abandoned in a daemon thread, which lives until the resolver returns. On Windows a read that is already waiting is not woken by the deadline's shutdown, so a call can last almost twice its limit. |
| Relay proxy: keys are plain text, and the token can re-point a role | Upstream keys are in `relay.json` (mode `0600` on POSIX only; Windows ACLs are not set). ### Security and privacy (see [09-security-privacy.md](09-security-privacy.md))

- Android API key and history are not encrypted inside the app's private storage.
- Windows history and meeting data are plain files.
- Dictated text passes through the clipboard (clipboard history can keep it). `keep_clipboard` defaults to false, so the old clipboard text is restored after a paste.

### Structure and quality

- `windows/engine.py` mixes hotkey, audio, tray, paste, control server and calendar in one class; `windows/meeting.py` mixes recording, speech, prompts, storage and search. Several flags (`Engine.busy`, `Engine.pending`, `Meeting.active`) are plain attributes read from other threads.
- `Meeting.attribute_speakers` updates `entries` without holding `lock`.
- `Engine.quit` waits at most 180 s for meeting notes, then exits anyway.
- `windows/ui/index.html` is one large script with global state; `android/assets/index.html` likewise.
- Almost no automated coverage outside the pure helpers (see [10-build-test-release.md](10-build-test-release.md)).
- The cleanup rules are implemented twice; `spec/golden.txt` guards them, but new rules must be added on both sides by hand.
- `Prefs` is created in many places; `DictationService.listener` is a static reference.

### Build and release

- CI runs the tests and the Android build on pull requests; the Windows build runs only on tags or by hand.
- Without the `ANDROID_KEYSTORE_B64` secret, a tag build fails and every other CI APK (`Vox-android-debug-key`) has a new signing key and cannot update an installed app.
- `windows/build_app.bat` installs an unpinned PyInstaller (CI pins one) and its failure text tells the user to "send it to Claude" (original wording).
- Uploaded audio is uncompressed WAV (about 32 KB per second of speech) on Windows; on Android clips of 4 s or more go up as m4a (not run on a phone yet).

## Roadmap (not started unless marked)

Ordered by how much they would help (the v2 plan; P1 to P4 are done):

1. Lighter builds, rest of P8a (the Pillow codec excludes are done: 85 MB to 77 MB, see [10-build-test-release.md](10-build-test-release.md)): numpy is 28 MB and needed by the meeting audio capture; Pillow's `_imagingft` (2 MB) and Tcl's `tzdata` (3 MB) could go; create the WebView window on demand; on Android drop the manual "start service" step (needs a device test; the APK is already 56 KB). Idle memory has not been measured.
2. Notes, rest of P5: the Windows voice notes store and page and the Android notes (store, note mode, Notes page; the phone is untested) are done; still to do are one list for dictations and meetings, tags in the UI, and a hotkey for notes.
3. Android note mode (P6): built (a persistent bubble without a text box, drawn by the accessibility service; a notification action and a Quick Settings tile; spec [p6](specs/p6-android-note-mode.md)) but not tried on a device; the Notes page that lists the notes is built too (not tried on a phone). Settings has the switches for the note bubble and the note notification (`note_bubble`, `note_notification`; both default to off). Also still to do: a boot receiver for the "Record note" notification, and a check of the lifecycle limits above. Test on Android 14 and 15 first: starting the microphone service from an overlay tap is not guaranteed.
4. Relay, rest of P7: the server, Windows voice-note sync, Windows profile sync and the Android client are done (see [14-relay.md](14-relay.md)); the Android client (notes and profile) is built (a saved note triggers a pass, spec [p7e](specs/p7e-android-sync.md)) but not tried on a phone; also still to do are a background scheduler for the phone, dictation history and meetings, per-app styles per platform, audio blobs, and trying it over real Tailscale. The relay's proxy routes and the "Use my relay as the AI server" switch on both apps are built (see [specs/p7f-relay-proxy.md](specs/p7f-relay-proxy.md)) but have only run against stand-in servers.
5.
