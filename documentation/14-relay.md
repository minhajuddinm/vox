# 14. The relay

An optional server the user runs on their own machine (PC, Raspberry Pi, any Linux box) so a phone and a PC can share voice notes and a profile. **This page describes what exists in the code today: the server, its management page, its proxy routes, the Windows client (voice notes, profile, and its speech and cleanup calls through the proxy routes) and the Android client (voice notes and the shared profile) and running the server from the Windows app.** The Android client is only compile-checked and tested off-device; it has not run against a relay on a phone. Both clients can also send their speech and cleanup calls through the proxy routes; nothing in the proxy path has run on a real phone, Raspberry Pi or Tailscale link. Set-up steps for a Raspberry Pi are in [../relay/README.md](../relay/README.md).

## What it is

`relay/relay.py`: one Python file, standard library only, no Vox imports, Python 3.9 or newer. It runs on Linux (including a Raspberry Pi 5, arm64), macOS and Windows; CI runs its tests on Python 3.9 and 3.13 on x86 Linux and on Python 3.13 on arm64 Linux. It listens on `127.0.0.1` only (there is no option to listen elsewhere). The Windows app can run it for you: `Vox.exe --relay` starts it (the exe bundles `relay.py`), and the tray item "Run relay on this PC" starts and stops that as a child process of Vox (see "Running it from Vox on Windows" below). The installer has no separate relay file or service. For a machine without Python, CI also builds standalone relay programs (see "Standalone relay programs" below).

| Item | Detail |
|---|---|
| Start | `python relay.py [--data-dir DIR] [--port N] [--owner LOGIN] [--show-token]`, or the same options after `Vox.exe --relay`; stops cleanly on Ctrl+C and on SIGTERM (systemd) |
| Files | `relay/relay.py`, `relay/vox-relay.service` (systemd unit for Linux), `relay/README.md` (set-up guide) |
| Data folder | Windows `%APPDATA%\VoxRelay`, macOS `~/Library/Application Support/VoxRelay`, elsewhere `$XDG_DATA_HOME/vox-relay` (default `~/.local/share/vox-relay`): `relay.json` (token, admin token, port, owner, AI server settings) and `relay.db` (SQLite, WAL). On POSIX the folder is `0700` and `relay.json` is created `0600`. |
| Reaching it | publish to the user's own tailnet: `tailscale serve --bg 8765` (HTTPS with a `*.ts.net` certificate, tailnet only). Never Funnel. |
| Auth | every data request needs `Authorization: Bearer <token>` (constant-time compare). If `owner` is set, the `Tailscale-User-Login` header (added by `tailscale serve`) must match it. The admin token (`admin_token` in `relay.json`, printed by `--show-token`) is accepted everywhere too and is the only one that can make a new token or change the AI server settings; devices never hold it. Before either app sends the token it asks `GET /proof` (below) and checks the answer. |
| Limits | body 1 MB (a bigger upload is read and dropped, up to 5 MB, then answered 413 so the client sees the answer); note text 100,000 characters (longer text is silently cut to that length, not refused with a 400); 20 tags; profile 64 KB; a connection that stalls for 30 s is dropped; the request line and headers must all arrive within 10 s of their first byte (an idle kept-alive connection is not on that clock); at most 64 connections at once (`MAX_CONNECTIONS`): a connection that has not sent the first byte of a request (new, or kept alive between requests) gives up its place when the relay needs it, after 2 s once half the places are taken (`IDLE_WHEN_BUSY`) and at once when a new connection finds all 64 taken (the one idle longest goes, so silent sockets from a local program cannot lock out sync and dictation); when all 64 are busy with requests the next is answered 503 and closed without a thread; a client that hangs up or is cut at the deadline prints no traceback; JSON with `NaN` or `Infinity` (or a number too large for a float) is refused with 400; `since` beyond 64 bits is a 400. On Windows the relay binds its port with `SO_EXCLUSIVEADDRUSE`, so no other program (no other Windows user either) can bind it while the relay runs. The proxy routes have their own limits (see below). |
| Logging | no access log (paths carry search words and note ids); the management page keeps the last 100 requests in memory only (method, path with ids replaced, result, device name; a refused request is listed as `(refused)` without its path, which is the sender's own text). No request or answer body is ever logged, including on the proxy routes. |
| Outgoing connections | only the proxy routes make any: one request at a time per call to the address saved for that role, with its key. Nothing else in the relay connects out. |

## Management page

`GET /` (or `/ui`) serves one HTML page with no data in it and no login of its own: it asks for the token in the browser and then calls the JSON endpoints below with it. The token is kept in `sessionStorage`, or in `localStorage` if "Remember on this device" is ticked. Tabs:

| Tab | Shows or does |
|---|---|
| Overview | notes, delete markers, database size, sync position, uptime, requests, errors, refused (bad token) requests, profile version, platform and Python, the `tailscale serve` command; refreshes every 10 s |
| Notes | search, list, delete one note, export everything as JSON |
| Devices and activity | devices that sent `X-Vox-Device` (last seen, request count, Tailscale user) and the last 100 requests |
| Profile | the profile with keys, tokens, secrets and passwords hidden (any JSON key containing `key`, `token`, `secret` or `password`) |
| AI server (proxy) | one block per role (speech to text, text cleanup): an address field, "key set: yes/no", a write-only key field, Save and Clear; the key is never shown again |
| Maintenance | download a backup of the database, compact it, purge old delete markers, make a new token (the old one stops working at once) |

The page is served with a Content-Security-Policy that allows only its own inline script and style through a fresh nonce per response, no framing, `connect-src 'self'`; it builds the page with `textContent` only, so note text is never interpreted as HTML (a test and a browser check with a `<script>` note confirm this).

## Protocol (JSON)

| Request | Meaning |
|---|---|
| `GET /proof?nonce=N` | No token. `{proof, version}` where `proof` is HMAC-SHA256 of `vox-relay-proof:N` keyed with the token (hex). `N` is 16 to 128 letters, digits, `-` or `_` (else 400). Both apps ask this before they send the token and send nothing when the proof is wrong, so a program squatting on the relay's port while the relay is down never gets it (`sync.prove_relay`, `RelayProof.java`). A good answer is kept for 10 s (`sync.PROOF_TTL`, `RelayProof.TTL_MS`) and asked again after a failed connection or a 502, 503 or 504 (what `tailscale serve` answers while the relay behind it is stopped); through the relay as the AI server every retry of a dictation asks again after such a failure, and a `/proof` request that got no answer is tried again like the upload. What is left: a program that takes the port the moment the relay stops, while no request has failed yet, can receive the token in the at most 10 s the last proof is still trusted. A relay from before this route answers 401: it is still used, and Test connection adds "This relay is too old to prove it holds the token ...: update it", until the address has once proved itself; from then on a missing proof is refused ("This relay proved it holds the token before and now does not ..."). The proofs reveal nothing about the token, but anyone who can reach the relay can ask for one, so a program that can reach the real relay could pass proofs on: that is outside this check. Not logged. |
| `GET /health` | `{ok, version, notes, seq}`. Needs the token like every route, so the apps' Test connection button uses it to learn at once that the relay is there, the token works and what version it is (a 401 means the relay is there and the token is wrong). |
| `GET /changes?since=SEQ&limit=N` | notes and delete markers written after `SEQ`, oldest first: `{notes, next, more}`. Clients keep `next` as their cursor. |
| `PUT /notes/{id}` | upsert one note (body = the note). The id in the path wins. Answer `{note, applied}`; `applied` is false when a newer or identical version is already stored. |
| `GET /notes/{id}` | one note (404 if unknown or deleted) |
| `DELETE /notes/{id}` | turns the note into a marker: content, title and tags removed, `deleted: true`, new sequence number; the answer is `{note, applied}`. The marker is stamped with the relay's clock and later than the stored `updated_at` (the relay's own act, so the clock bound below does not apply), so a note whose time is ahead of the relay's clock, even one an older relay stored a week ahead, is still deleted |
| `GET /notes?q=&tag=&from=&to=&limit=` | search (words match as word starts, all must match; times are epoch seconds), newest first, deleted notes excluded |
| `GET /devices` | `{devices: [{name, first_seen, last_seen, requests, login}]}`, newest first (epoch seconds): the devices that sent `X-Vox-Device` on any request. Needs the token like every route (and the owner check when set); same fields as the management page's Devices table (`login` is the Tailscale user the relay saw); no events, no notes. Used by the Devices card in the apps. |
| `GET /profile` | `{version, data}`; version 0 and empty data before the first save |
| `PUT /profile` with `If-Match: VERSION` | replaces the profile if `VERSION` is current (`0` or `*` for the first save). 200 with the new version; 412 with the current profile when stale; 428 when `If-Match` is missing. |
| `GET /admin/status` | numbers for the Overview tab |
| `GET /admin/activity` | `{events, devices}` |
| `GET /admin/profile` | the profile with secrets hidden |
| `GET /admin/export` | all live notes as a JSON download |
| `GET /admin/backup` | a consistent copy of `relay.db` (SQLite backup API) as a download |
| `GET /admin/upstream` | `{stt: {base_url, key_set}, llm: {base_url, key_set}}`: the AI server address of each role and whether a key is stored; never the key |
| `PUT /admin/upstream` with `{role, base_url, api_key?}` | admin token only (403 with the device token); sets one role (`stt` or `llm`); `api_key` omitted keeps the stored key (only while the address is unchanged), `""` clears it; `base_url` `""` clears the address and the key. Answer: the same shape as the GET. 400 with a message for a bad role, address or key; 409 when the relay has no data folder. |
| `POST /admin/vacuum` | compacts the database |
| `POST /admin/purge` with `{days}` | forgets delete markers older than `days` |
| `POST /admin/rotate-token` | admin token only (403 with the device token): writes a new token to `relay.json` and adopts it; answer `{token}`. The admin token stays. |
| `POST /proxy/stt/audio/transcriptions`, `GET /proxy/stt/models`, `POST /proxy/llm/chat/completions`, `GET /proxy/llm/models` | forwarded to the role's AI server; see "Proxy routes" below |

Any client may send `X-Vox-Device: <name>` on every request so the page can show which devices use the relay. A header is latin-1, so both apps send the name in the Android spelling (every character outside printable ASCII becomes `?`; `sync._ascii_name`, `RelayClient.headerText`): a PC named with a typographic apostrophe is listed as `Sam?s PC`, and the Devices card still marks it as this device. The `/admin` endpoints take the device token or the admin token; `POST /admin/rotate-token` and `PUT /admin/upstream` need the admin token (so a stolen phone's token cannot lock the owner out or choose where the dictations go), and `GET /admin/status` says `admin: true` when the admin token was used.

Note fields: `id` (32 lowercase hex characters, made by the client), `source`, `title`, `text`, `raw`, `created_at`, `updated_at` (epoch seconds; more than a day ahead of the relay's clock, for example milliseconds, is a 400; up to a day ahead is accepted and stored as sent, but when writes are compared it counts as no later than the relay's clock plus 5 seconds, `MAX_CLOCK_SKEW`), `secs`, `device`, `tags` (list), `deleted`; the relay adds `seq`.

## Rules

- **Conflicts:** the write with the larger `updated_at` wins; on a tie the later arrival wins; an identical repeat changes nothing and gets no new `seq`. A delete marker written with a later `updated_at` beats an older edit. A phone with a fast clock cannot pin a note: for the comparison its time counts as no later than the relay's clock plus 5 s (kept in a column of its own, `order_at`, never sent; [decision 0040](decisions/0040-the-relay-stores-the-sent-note-time-and-orders-by-a-bounded-copy.md)), and a note that an older relay stored further ahead is replaced by any write made in the last 5 minutes by the relay's clock (`RECENT_WRITE`), a device's delete marker (a `PUT` with `deleted: true`) included. The `updated_at` that devices see is stored as the device sent it, and a write that wins is raised just above the stored one, so every device takes it, the fast phone included (an earlier version stored the cut-back time instead, and the fast phone then ignored every later change from the other devices). An older write still loses.
- **Sequence numbers:** the relay assigns `seq` (SQLite `AUTOINCREMENT`), so clients never compare clocks with each other to know what is new.
- **Deletes:** kept as markers with no content so other devices learn about them. Purging markers means a device that was offline for longer than the purge age could bring a deleted note back.
- **Profile:** an opaque JSON object; the relay does not look inside. If clients put API keys in it, they sit in `relay.db` unencrypted (see [09-security-privacy.md](09-security-privacy.md)).

## AI server settings (proxy mode)

Each role, `stt` (speech to text) and `llm` (text cleanup), can have an address and a key for an OpenAI-compatible server. They live in `relay.json` under `upstream` (see [07-config-and-data.md](07-config-and-data.md)); `rotate-token` and every save keep the rest of the file. The proxy routes below use them; the page and `GET /admin/upstream` show the address and whether a key is set, never the key.

- **Address rules** (`upstream_problem` in `relay.py`; a short copy of the app's rule in `windows/vox_core.py`, because the relay cannot import app code): `http` or `https` only, a host, no user name or password, no query and no fragment (the relay will add fixed paths), no spaces or non-ASCII characters, at most 2048 characters. Plain `http` only for this machine, the home or office network and Tailscale (loopback, private and link-local addresses, `100.64.0.0/10`, one-label names, `.local`, `.lan` and `.ts.net` names; a host whose last label is a number, such as `134744072` or `0x08080808`, is not a name and needs `https`); any other server needs `https`. For a plain `http` name, the relay connects only to the addresses it resolves to that are in those ranges (`_open_socket`; a LAN name's global IPv6 address is skipped), and a name with none is a 502 with nothing sent. A trailing `/` is dropped. The error messages never repeat the address.
- **The key is write-only.** It is stored in `relay.json` in plain text (mode `0600` on POSIX), used only by the relay, and returned by no endpoint: not by `/admin/upstream` (only `key_set`), `/admin/status`, `/admin/activity`, `/admin/profile`, `/admin/export`, `/admin/backup` (the database does not hold it), `/profile`, error messages or the process output; tests check each of these. A key is 1 to 1024 printable ASCII characters without spaces (surrounding spaces are trimmed).
- **A key belongs to its address.** Saving a different address without a new key removes the stored key, so a device that holds the token cannot point a role at another server and have the old key sent there. To move a role and keep working, send the new address together with its key.
- Saves are written through a temporary file and a rename, one at a time, so `relay.json` is never half written.

## Proxy routes

Four routes let a client make its speech-to-text and text-cleanup calls through the relay, so the API key stays on the relay and the client only needs the relay token. They use the role's address and key from the settings above.

| Request | Forwarded to |
|---|---|
| `POST /proxy/stt/audio/transcriptions` | `<stt address>/audio/transcriptions` (multipart audio upload) |
| `GET /proxy/stt/models` | `<stt address>/models` |
| `POST /proxy/llm/chat/completions` | `<llm address>/chat/completions` (JSON) |
| `GET /proxy/llm/models` | `<llm address>/models` |

- **The upstream URL is fixed.** It is the saved address plus the suffix in the table and nothing from the request: the path must equal a route exactly and the method must match (no decoding, no `..`, no `//`, no `;params`, no extra segments, no absolute-form target); anything else under `/proxy/` is 404. A query string is ignored and never forwarded.
- **Order of checks.** Token (401) and owner (403) come first, before anything else, even where the role is not configured. Then: unknown route 404, unusable body framing 411 or 400, role not configured 503, body too large 413, no free slot 429, then the upstream call.
- **What is sent upstream.** `Content-Type` (this keeps the multipart boundary; POST only), `Accept`, `Content-Length`, `User-Agent: vox-relay`, and `Authorization: Bearer <key>` only when a key is stored. Nothing else of the client's request goes on: its own `Authorization` (the relay token), `Tailscale-User-Login`, `X-Vox-Device`, cookies and forwarding headers stay behind, and a copied header value must be printable ASCII. The key goes only to the address of its own role. Outgoing connections use `http.client`; `https` addresses check the certificate (the default context, never switched off). A redirect from the upstream is not followed (502).
- **What comes back.** The upstream status and body. Of its headers only `Content-Type` and `Retry-After` are copied (an upstream 429 keeps its `Retry-After`; the relay's own "busy" 429 is told apart by its body). The answer is read whole, up to 8 MB (more is a 502), so streaming answers are not supported. If the upstream repeats the key in its answer, as some servers do in error messages, the key is replaced with `***` (keys under 8 characters are not covered). Answers carry `Content-Security-Policy: default-src 'none'; sandbox`.
- **Timeouts** are for the whole exchange (name lookup, connect, upload, wait, download): 180 s speech to text, 240 s text cleanup, 15 s model lists (each at least as long as the longest wait of any client: the meeting recorder waits 180 s for speech and the meeting notes 240 s; dictation waits 60 s). The lookup and the connection attempts share the one deadline, and once connected a timer shuts the connection down when the time is up. That is what stops an upstream that keeps a reply moving so that no single read times out (endless `100 Continue` lines, a status line one byte at a time, trailer lines without end) from holding one of the four slots for ever; a reply that ends at the cut-off is never passed on as a success. On Linux a shut-down connection wakes a waiting read at once, so the cut is at the deadline (only CI runs the tests there; they were written and run on Windows). On Windows it does not wake it, so a read that is already waiting ends with its own timeout, which is never longer than the time left when it started: there the total can be almost twice the limit. A name lookup that never ends is abandoned at the deadline (its helper thread ends when the system resolver does and holds no slot). An upstream that is unreachable, too slow, hangs up or sends less than it promised gives 502 with `{"error": {"message": "upstream unreachable"}}` (the OpenAI shape, so the apps' existing error path shows the message; it never contains the address).
- **Limits.** Request body: 25 MB for speech to text, 1 MB for text cleanup; both need a `Content-Length` (missing is 411, and chunked uploads are not supported, also 411: the apps build the multipart body with a known length for this reason; `ApiClient.transcribe` uses `Multipart` and `setFixedLengthStreamingMode`). A refused chunked or badly framed upload is read for a moment and dropped (it cannot be skipped) and the connection ends after the answer, so the client sees the 411 and not a reset. Too large is 413 by the same rule as the notes endpoints: up to 5 MB of the upload is read and dropped, and only while it keeps arriving, so the client sees the 413 and not a broken pipe. A body on a GET is read and dropped. At most 4 calls hold a slot at once and at most 8 exchanges (each holds its request body in memory until the request has been sent upstream, and only its connection after that: `forward_upstream` lets go of the body) are alive at one time (`proxy_running`, twice `PROXY_SLOTS`); the extra 4 exist only on Windows, while abandoned reads run out. The next call gets 429 `{"error": "busy"}` at once. **A client that hangs up frees its slot.** While the relay waits for the upstream it looks at the client's connection every 0.25 s (`CLIENT_POLL`); when the client has gone, the upstream exchange is shut down, nothing is answered (the activity list shows status 499) and the slot is given back at once. On Windows a read that is already blocked on the upstream is not woken by the shutdown and ends with its own timeout; the slot is released at once anyway, but the exchange (and its body) still counts against the 8 until that read ends. This stops the apps' abandoned requests (they give up after 60 s) from filling the four slots while a slow upstream is still thinking. The apps do not send a request again after a timeout when the relay is the AI server (see [06-pipeline.md](06-pipeline.md)).
- **Errors made by the relay** use `{"error": "text"}` like the rest of the relay: 400 (bad or repeated `Content-Length`, body cut short), 404, 411, 413, 429, 503 ("not configured": the role has no address, or `relay.json` holds one that fails the address rules). An upstream's own errors pass through unchanged.
- **Device counting and activity** work as for every other request (`X-Vox-Device`); no request or answer body is logged or kept.

## Clients

- **Windows:** `windows/sync.py` (settings `relay_sync`, `relay_url`, `relay_token`, `device_name`). It sends changed voice notes with `PUT /notes/{id}`, fetches `GET /changes` from its stored cursor and merges by `updated_at`; an edit or delete made on the PC is stamped later than the version it changes even when the PC clock is behind (`notes._stamp`). It keeps a `next` only when it is a whole number larger than the cursor (otherwise the pull stops for that run), and before sending it compares the relay's `GET /health` `seq` with the cursor: a relay below it lost its data at the same address, so the PC starts over and sends every note again. It runs at start, every 90 seconds and after each saved note, and sends `X-Vox-Device`. See [decisions/0022-sync-client-dirty-flag-and-cursor.md](decisions/0022-sync-client-dirty-flag-and-cursor.md). A note the relay refuses for good (a 4xx other than 401, 403 and 429, for example 400 for a bad id) is skipped for that run and reported ("1 note could not be sent: ..."); it stays `dirty`, is tried once more in every later run, and does not stop the other notes, the pull or the profile. Any other failure (network, 401, 403, 429, 5xx) stops the run and keeps what was done.
- **Profile:** the same client also syncs the profile document (`GET`/`PUT /profile` with `If-Match`): a fixed set of settings merged field by field, provider settings and keys only when `relay_sync_keys` is on. See [decisions/0023-profile-sync-three-way-merge.md](decisions/0023-profile-sync-three-way-merge.md).
- **The relay as the AI server (Windows):** Settings, AI provider, switch "Use my relay as the AI server" (`relay_proxy`). With it on, the dictation, model list, warm-up and Test calls go to `<relay_url>/proxy/stt/...` and `<relay_url>/proxy/llm/...` with the relay token in `Authorization` (no provider key is sent), so the provider key lives on the relay only (set on its management page, AI server (proxy) tab) and the provider address and key fields are hidden in Settings. The status line under the switch says "Turn on the relay first" until the relay address and token are filled in (they are entered under Sync between devices; `relay_sync` need not be on) and then shows the address in use. The relay's 401 (wrong token) and an AI server's 401 or 403 (wrong key on the relay, passed through unchanged) both show "check the relay token and the AI server key set on the relay page". The relay has no other requirement: it needs the AI server addresses and keys set for both roles, else it answers 503 "not configured". Details and the exact rules: [06-pipeline.md](06-pipeline.md). Tests: `tests/test_providers.py` check the routes used, the headers and that no provider key goes to the relay.
- **Test connection and the set-up card (both apps):** the Test button asks `GET /health` with the saved or typed address and token and this device's name in `X-Vox-Device`, so a good test also puts the device in the relay's list. It reports `ok`, `reachable`, `token_ok`, `device_name`, `relay_version` and the notes count (`sync.relay_check` / `RelayCheck.of`; rules and edge cases in the `relaycheck` golden rows). The collapsible card "How to set up the relay" in Settings shows the same steps as [../relay/README.md](../relay/README.md); both come from the commands in `ui-shared/relay-steps.txt` (the README is written by hand and `tests/test_ui_relay_help.py` fails when a command of the card is missing from it).
- **Devices on my relay (both apps):** `GET /devices` with the saved address and token and this device's name in `X-Vox-Device` (`sync.fetch_devices`; Android `RelayClient.listDevices`). The apps turn the list into rows `{name, this, state, ago}` with one rule (`sync.devices_view` / `DevicesView.rows`, `devices` golden rows): active under 10 minutes, recent under a day, else old. They draw only those four fields, never `login`. A relay that answers 404 gets "This relay is too old to list devices."; any failure is an empty list and the reason. The card asks by itself only while "sync notes" or "Use my relay as the AI server" is on; Refresh and a good Test always ask. A phone that has never sent its name is not in the list, and Android's name shows with `?` for characters outside printable ASCII (the relay lists it that way; the view matches it). Spec: [specs/p9c-devices-and-relay-setup.md](specs/p9c-devices-and-relay-setup.md); decision [0034](decisions/0034-devices-list-is-the-relays-own-list-asked-on-a-switch-or-a-press.md).
- **Android:** `SyncEngine`, `RelayClient`, `SyncWorker` (`android/src/com/minhaj/vox/`), the same protocol and rules as the Windows client: notes and profile, `X-Vox-Device` and the bearer token on every request, runs when the app opens, when the dictation service starts, when settings are saved and every 90 seconds while the process lives (no background scheduler: a phone that never opens the app syncs at the next open). The phone keeps the dictionary and people as text with one entry per line and shares them as lists; `llm_reasoning` is not a phone setting and is left alone. One rule the Windows client does not have yet: before each run with a saved cursor the phone asks `GET /health`, and a `seq` below its cursor means the relay at that address lost its data (wiped, or restored from an older backup), so it resets its sync state as for a new relay and sends every note again. Details and the field table are in [05-android-app.md](05-android-app.md), "Relay sync". `RelayIntegrationTest` runs this client against the real `relay/relay.py` (see [10-build-test-release.md](10-build-test-release.md)). The Android switch "Use my relay as the AI server" (`relay_proxy`, Settings, AI provider) sends dictation, model lists, warm-up and the Test buttons to the proxy routes the same way as on Windows (see above and [06-pipeline.md](06-pipeline.md)); the provider address and key rows are hidden while it is on.

## Running it from Vox on Windows

The tray menu has a checkbox **Run relay on this PC** (setting `relay_run`, port `relay_port`, default 8765). Ticking it makes the engine start `Vox.exe --relay --data-dir %APPDATA%\VoxRelay --port 8765` as a hidden child process; unticking it, or quitting Vox, stops it. If `relay_run` is on, the relay starts whenever Vox starts. The data folder is the relay's own default, so the token is in `%APPDATA%\VoxRelay\relay.json`, and a relay started by hand with `python relay.py` and the one Vox starts are the same relay (only one can use the port at a time).

- The first time it ever starts (no `relay.json` yet) a tray notification gives the exact command to reach it from the phone: `tailscale serve --bg 8765` (with the real port). Vox does not run that command itself.
- If something already answers on the port (for example a relay you started by hand), Vox does not start a second one and a tray notification says so. If the relay process ends within 10 s of starting, a tray notification says so; `%APPDATA%\Vox\relay.log` has the reason. (The check exists because `relay.py` binds with `SO_REUSEADDR`, which on Windows lets a second relay take a busy port without an error.)
- The child cannot outlive Vox: it is stopped on quit and is tied to Vox by a Windows job object, so it also ends if Vox is killed or crashes. The relay is still bound to `127.0.0.1` only.
- The PC's own Vox does not point its sync at this relay automatically: enter the relay's address and token in Settings like any other device.
- Design of the process handling: [windows/relay_host.py](../windows/relay_host.py); details in [04-windows-app.md](04-windows-app.md).

## Standalone relay programs

Job `relay-exe` in `.github/workflows/build.yml` freezes `relay/relay.py` with PyInstaller `--onefile` (console program, no extra packages, a few unused standard-library modules excluded) into `vox-relay-windows-x64.exe` (`windows-latest`), `vox-relay-linux-x64` (`ubuntu-latest`) and `vox-relay-linux-arm64` (`ubuntu-24.04-arm`, for a Raspberry Pi 5 with the 64-bit Raspberry Pi OS). Each is uploaded as an artifact of the same name; job `relay-sums` adds `SHA256SUMS.txt` (artifact `SHA256SUMS`), and on a tag build the release job attaches the three files and the sums. Each program is smoke-tested in its own job before upload by `tools/relay_smoke.py`: `--help` exits 0, then it is started on `127.0.0.1` with a temporary data folder and `--show-token`, `/health` must answer 401 without the token and 200 with it, then it is stopped. The options and data-folder defaults are those of `relay.py`; as the systemd service it uses the same unit file with `ExecStart` pointing at the file (see [../relay/README.md](../relay/README.md), "Standalone relay (no Python)"). **Unverified on a real Raspberry Pi, under the systemd unit and through `tailscale serve`;** only the CI smoke test has run. Downloaded Linux files need `chmod +x` (an artifact zip does not keep the mark). The Windows app does not use these files: it still bundles `relay.py` as `Vox.exe --relay`.
